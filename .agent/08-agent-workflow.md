# 08 Agent 工作流（三个独立会话 + 学生把关）

题目要求：开发、测试、验收三个 Agent 角色必须使用**相互独立的会话或任务上下文**；Test/Acceptance 必须读取原始题面和对应版本代码，不能只依据开发 Agent 的完成声明判断通过。本文件规定交接物、可改范围、必须向学生确认的事项和返工回路。

## 1. 三个会话的职责与边界

| 会话 | 必读输入 | 允许写入 | 明确禁止 | 交付物 |
|---|---|---|---|---|
| Dev（开发） | 题面、AGENTS.md、`.agent/01–06`、需求/假设/原型/任务清单 | 业务代码、迁移、页面、测试、文档 | 改题目规则；自宣测试通过/验收；推 `main`；加未确认依赖 | 代码提交、任务记录、测试初稿、缺陷修复、部署配置 |
| Test（测试） | 题面、`.agent/01–06`、**指定提交 SHA** 的代码、需求文档 | 测试文件、测试计划、缺陷记录、测试报告 | 修生产代码；改需求；依据 Dev 的口头声明 | `docs/acceptance/test-report-<sha>.md`、缺陷清单、原始测试输出 |
| Acceptance（验收） | 题面原文、`.agent/11`、**发布提交 SHA**、全部证据 | 只读；仅写验收报告 | 改代码、改测试、改需求、代签结论 | `docs/acceptance/acceptance-report-<sha>.md`（逐项结论 + 证据位置） |

派发任务时给每个会话的提示词模板必须包含：`角色、必读文件列表、目标提交 SHA、允许修改范围、必须产出的文件、禁止事项、完成判定`。

## 2. 阶段与交接门（按顺序执行）

```
需求分析 ──交接①──> 原型 ──交接②──> 任务规划 ──交接③──> Dev 开发 ──交接④──> Test 独立测试
   ──交接⑤（缺陷回 Dev）──> Dev 修复 ──交接⑥──> Test 复测 ──交接⑦──> Acceptance 验收
   ──交接⑧（问题回 Dev）──> PR 合并 ──交接⑨──> 主分支重新门禁 + 自动部署 + 冒烟 ──交接⑩──> 视频/提交
```

| 门 | 交接物 | 学生必须亲自确认 |
|---|---|---|
| ① | `docs/requirements.md`、状态图、`docs/assumptions.md` | 规则编号与题面逐条对应；假设合理 |
| ② | `docs/prototype/` 原型 + 页面状态说明 | 四个角色页面可操作、异常可见 |
| ③ | `docs/tasks.md` + `.agent/development/` 任务记录 | 任务拆分可 8 小时完成，依赖与验收条件明确 |
| ④ | 开发提交 SHA + 任务记录 + 自测输出 | 代码逐段审核；拒绝“能跑就算完成” |
| ⑤ | Test 报告 + 缺陷编号 + 复现步骤 | 缺陷严重级别与是否阻塞 |
| ⑥ | 修复提交 SHA + 复测对比 | 修复不弱化规则，不删测试 |
| ⑦ | 验收报告逐项 PASS/FAIL | 失败项是否必须返工（不允许“整体挺好”式通过） |
| ⑧ | PR 内容与检查结果 | 无越界改动、无敏感信息 |
| ⑨ | 流水线运行、部署 SHA、冒烟输出 | 部署版本 = 合并版本；回滚可用 |
| ⑩ | 视频、会话导出、事件 JSONL、skill-usage | 可复现、可追溯、无编造 |

## 3. 必须向学生确认的事项（Agent 不得自行决定）

1. 题目未明确、需要新假设（如：被拒后能否再次提交取消申请；退款超时按失败还是处理中）。
2. 表结构/状态枚举/接口契约变更；接口新增或字段语义变化。
3. 新增第三方依赖、引入新组件（消息队列、缓存、ORM 等）。
4. 覆盖率排除项；测试范围调整；跳过任何必需检查。
5. 业务规则放宽、并发策略取舍（行锁 vs 乐观锁）带来的可观察差异。
6. 合并方式、部署目标、回滚方案。
7. 验收 FAIL 项的豁免（仅教师规则允许时；学生记录理由）。

确认必须落在任务记录或 `docs/assumptions.md`，包含时间、问题、选项、学生决定。

## 4. 返工回路

- Test/Acceptance 发现缺陷：写缺陷记录（模板）→ 交回 Dev → Dev 修复并引用缺陷编号 → Test 用**同一复现步骤**复测 → 记录修复前后输出 → 关闭。
- 验收失败项：回到开发分支修复，重新走 PR 检查与部署；不得直接改 `main`。
- 每次返工都保留原失败证据，不允许覆盖或删除；历史失败与最终通过并存。

## 5. 防止“Agent 自说自话”的机制

- Test 会话必须**独立复读题面**并自行列检查项，不得复制 Dev 的完成清单当测试计划。
- Acceptance 会话按 `.agent/11` 逐项验证，每项必须给“证据位置 + 结论”，缺失证据一律 FAIL，不得写“应该没问题”。
- 所有“通过”必须附命令输出/文件路径/截图索引；Agent 自述不作为通过依据。
- 学生至少演示一次“Skill/AI 发现问题 → 指导修正 → 重新检查”的完整过程，并留证据（09/10）。

## 6. 会话启动提示词模板（可直接复制）

```text
你是本题的【测试 Agent】，与开发会话相互独立。
必读：题目原文（docs/requirements-original.md）、AGENTS.md、.agent/01–06、.agent/11；
目标版本：dev/02-* 分支提交 <SHA>（工作区已 checkout，禁止修改生产代码）。
任务：依据题面自行制定测试计划，覆盖规则 R1–R8、权限 P1–P7、并发 C1–C10、覆盖率门禁；
产出：docs/acceptance/test-plan-<SHA>.md、test-report-<SHA>.md、缺陷记录（模板）；
只允许新增/修改 *_test.go 与测试数据脚本；发现业务代码缺陷只登记，不修复。
完成后列出：执行命令、原始输出路径、覆盖率、未通过项与证据位置。
```

> 验收会话模板同理，把角色改为“验收 Agent”、允许写入改为仅验收报告、并强调“逐项对照 `.agent/11`，缺证据即 FAIL”。
