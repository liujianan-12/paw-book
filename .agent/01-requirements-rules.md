# 01 需求与业务规则（唯一可测试口径）

本文件把题目原文拆成**带编号、可断言**的规则。代码注释、测试名、缺陷、验收项一律引用编号；任何解释冲突以题目原文为准，并在 `docs/assumptions.md` 记录。

## 1. 角色与业务起点

| 角色 | 能做什么 | 不能做什么 |
|---|---|---|
| 店长 | 发布/查看时段；时段结束后标记未到店并写原因；查当日经营与收款核查 | 代替前台核销、代替客服审批 |
| 宠物主人 | 选择自己的宠物预约、付款、取消、提交取消原因、查看预约/退款/服务结果 | 操作他人宠物；越过取消规则 |
| 前台 | 核销本店、已确认、无待处理取消申请的预约 | 核销别店；核销未付款/已取消 |
| 服务人员 | 登记服务开始、完成 | 跳过核销直接开始 |
| 客服 | 查看待处理取消申请；批准/拒绝；跟进并重试退款失败 | 改金额；让已取消预约恢复可用 |
| 模拟支付渠道 | 返回支付成功/失败/超时；重复通知；退款成功/失败/超时 | 真实资金 |

预置数据：1 门店、1 洗护项目（9900 分）、3 个未来时段（每时段容量 3）、预置用户与宠物。不实现档案编辑、优惠、会员、排班、多店结算。

## 2. 规则编号与可验证条件

### R1 时段与预约资格
| 编号 | 规则 | 可验证断言 |
|---|---|---|
| R1.1 | 店长创建时段必须给出起止时间 | 缺 `startAt/endAt`、`startAt>=endAt` 时创建失败并返回明确错误 |
| R1.2 | 同一宠物同一时段只能有一个**有效**预约 | 并发/串行重复预约同一宠物+同一时段，第二次被拒绝；数据库有唯一约束兜底 |
| R1.3 | 名额不足不可预约 | 第 4 条有效预约被拒绝，时段有效预约数恒 ≤ 每时段容量（3） |
| R1.4 | 时段已开始不可预约 | 教学时钟 ≥ `startAt` 时预约被拒绝 |

### R2 未付款占位与支付
| 编号 | 规则 | 可验证断言 |
|---|---|---|
| R2.1 | 未付款预约占用名额 5 分钟 | 预约创建后状态为待支付，`payExpireAt = createdAt + 5min`，有效预约数 +1 |
| R2.2 | 超时释放名额 | 教学时钟推进 5 分钟后，该预约变为已过期，有效预约数 -1，且只释放一次 |
| R2.3 | 主动取消（未付款）释放名额 | 取消后名额恢复，不产生退款 |
| R2.4 | 有效付款后成为已确认预约 | 支付成功 → 预约已确认，`paidAt` 有值，金额=9900 分 |
| R2.5 | 重复支付通知不得重复确认 | 同一渠道流水重复回调：预约不重复确认、不重复记收款、接口幂等成功 |
| R2.6 | 关闭后收到支付成功：登记异常并退款，不恢复预约 | 已过期/已取消的预约收到成功回调 → 生成异常支付记录 + 退款单（原因=关闭后支付），预约状态不变 |
| R2.7 | 支付失败可在占位窗口内重试 | 失败后重新发起支付 = 新支付流水（新 `order_no`），预约仍为待支付；同一预约最终最多一条成功支付；超过 5 分钟再支付成功按 R2.6 处理 |

### R3 取消政策
| 编号 | 规则 | 可验证断言 |
|---|---|---|
| R3.1 | 开始前 ≥2 小时取消已确认预约，全额退款 | 教学时钟 ≤ `startAt-2h` 时取消：自动受理，生成全额退款 9900 分 |
| R3.2 | 开始前 <2 小时取消须提交原因并由客服审核 | 缺原因被拒绝；提交后生成待审核取消申请 |
| R3.3 | 待审核期间保持名额且不得核销 | 取消申请待处理时，前台核销被拒绝；名额仍被占用；有效预约数不减 |

### R4 取消结果与退款
| 编号 | 规则 | 可验证断言 |
|---|---|---|
| R4.1 | 取消获准后不得到店核销 | 客服批准后，核销被拒绝且无核销记录 |
| R4.2 | 名额仅释放一次 | 批准、重复点击、退款重试都不会二次扣减名额；报名数可回算 |
| R4.3 | 退款状态独立可查询 | 用户/客服可查退款单状态（待处理/处理中/成功/失败/重试次数/原因） |
| R4.4 | 退款失败需跟进，且不得让已取消预约重新可用 | 退款失败后预约仍为已取消，不能核销/不能恢复；客服可重试，成功后金额与记录一致 |

### R5 核销与服务
| 编号 | 规则 | 可验证断言 |
|---|---|---|
| R5.1 | 前台只能核销本店、已确认、无待处理取消申请的预约 | 跨店、未付款、已取消、待审核取消四种情况核销均被拒绝 |
| R5.2 | 核销后服务人员可登记开始与完成 | 未核销不能开始；完成时记录完成时间与操作者 |
| R5.3 | 重复核销/完成不重复记收入 | 重复请求幂等，只有一条核销记录、一条服务记录、一次收入确认 |

### R6 并发与唯一结果
| 编号 | 规则 | 可验证断言 |
|---|---|---|
| R6.1 | 核销与取消同时发生时得到唯一合法结果 | 并发压测（≥10 轮）：要么核销成功、取消失败；要么取消成功、核销失败；没有两者都成功或都失败且数据不一致 |
| R6.2 | 已核销、服务中、已完成的预约不能再走取消退款流程 | 三个状态下取消均被拒绝；不产生退款单 |

### R7 未到店
| 编号 | 规则 | 可验证断言 |
|---|---|---|
| R7.1 | 时段结束后仍未到店的预约，由店长标记未到店并写原因 | 时段未结束/无原因时标记失败；成功后有操作者与原因 |
| R7.2 | 未到店不自动退款 | 标记未到店不生成退款；已收款保留，可由日清核查 |
| R7.3 | 用户可查看未到店结果 | 用户接口返回未到店状态与原因（脱敏） |

### R8 店长日清与金额核查
| 编号 | 规则 | 可验证断言 |
|---|---|---|
| R8.1 | 查询当日各时段有效预约、已完成、取消、未到店、退款待处理 | 日清接口按“时段”分组返回五类计数，合计可回算 |
| R8.2 | 已收款、已退款、未退款金额可从记录核查 | 三金额分别来自支付成功记录、退款成功记录、差额；可下钻到单据 |
| R8.3 | 不能把所有已付款都计作已完成服务 | 已完成服务金额仅统计已完成预约；已确认未服务、已退款、待退款分别列示 |

## 3. 状态机（与 05 一致）

```
                      ┌──(5min超时)──> 已过期(EXPIRED)
待支付(PENDING_PAYMENT)┤
                      ├──(用户取消)──> 已取消(CANCELLED)
                      └──(支付成功)──> 已确认(CONFIRMED)
已确认 ──(≥2h取消)──> 已取消(自动受理) ──> 退款(成功/失败)
已确认 ──(<2h取消,提交原因)──> 取消审核中(CANCELLATION_REVIEW)
    ├──(客服批准)──> 已取消 ──> 退款
    └──(客服拒绝)──> 已确认
已确认 ──(前台核销)──> 已到店(CHECKED_IN) ──(开始)──> 服务中(IN_SERVICE) ──(完成)──> 已完成(COMPLETED)
已确认 ──(时段结束+店长标记)──> 未到店(NO_SHOW)
已过期/已取消 + 支付成功回调 ──> 状态不变 + 异常支付 + 退款
```

## 5. 默认假设（未明确事项，需在实现前确认或记录）

1. 时段容量固定 3（题面），不支持超卖；日清按**时段开始时间**归属“当日”。
2. `<2h` 取消：同一预约同一时刻最多一条待审核取消申请；**被客服拒绝后可再次提交**（题面未禁止），每次提交保留原因、时间与决定记录。此为对原假设 A2 的覆盖，决定记录见 `docs/assumptions.md` D3。
3. 退款渠道超时按“失败”处理（错误码 `CHANNEL_TIMEOUT`），客服可重试；退款失败不影响取消状态。
4. 已确认未到店由店长在时段结束后手动标记，无自动 job 替代。
5. 支付成功但预约已关闭时，退款原因固定为“关闭后支付”，只登记异常，不恢复预约。
6. 金额一律整数分（9900 分），不做浮点；退款金额 ≤ 原支付金额。
7. 所有“当前时间”来自教学时钟（05），阈值 5 分钟/2 小时/时段起止都用同一时钟。
8. 角色身份来自预置账号的会话；员工数据范围限定在本店。

> 以上假设与题目有冲突时，以题目原文为准并更正，不得把假设当既定需求。
