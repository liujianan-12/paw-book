# 题目 02 需求说明：宠物门店的预约、接待、服务与取消退款

> 项目代号：paw-book
> 本文档为需求分析阶段产物，是后续原型、开发、测试、验收的唯一依据。

## 1. 业务概述

一家宠物护理门店通过 O2O 平台接受洗护预约。平台围绕"预约 → 支付 → 到店核销 → 服务履约 → 取消退款"这条主线，让宠物主人、前台、服务人员、客服、店长五方在同一份业务记录上协作，并保证每个时段的接待名额、每一笔款项去向可核查。

## 2. 角色（Participants）

| 角色 | 职责 | 不做的事 |
|---|---|---|
| 店长 | 发布可预约时段（明确起止时间）；标记未到店；查询当日经营结果（有效预约、已完成、取消、未到店、退款待处理及金额核查） | 不处理取消审核 |
| 宠物主人 | 为自己的宠物预约、付款、取消、查看预约与服务结果 | 不能编辑宠物档案（预置） |
| 前台 | 核验到店（核销）：仅限本店、已确认、无待处理取消申请的预约 | 不能核销已取消/未支付/审核中的预约 |
| 服务人员 | 登记服务开始、服务完成 | 不能核销 |
| 客服 | 审核临近开始（<2 小时）的取消申请；跟进退款失败 | 不做争议退款裁决 |
| 模拟支付渠道 | 返回支付/退款结果（可控模拟：成功、失败、超时、重复通知） | — |

## 3. 预置数据（教学固定）

- 1 家门店、1 个洗护项目、3 个未来时段
- 每时段最多接待 **3** 只宠物
- 预约款 = 本次服务全款 **9900 分**（99.00 元）
- 用户与宠物资料预置，不做档案编辑
- 不做：优惠、会员、排班优化、多店结算、真实短信

## 4. 核心业务规则

### 4.1 时段与名额
- R1 店长创建时段须明确起止时间。
- R2 用户为**自己的**宠物预约；同一宠物同一时段只能有一个**有效**预约（有效 = 待支付、已确认、核销后各状态）。
- R3 每时段有效预约数达到 3 只后不可预约；时段已开始后不可预约。
- R4 未付款预约**占用名额 5 分钟**；超时或用户主动取消后释放名额。
- R5 并发抢位必须保证名额不超卖（同一时段有效预约数 ≤ 3）。

### 4.2 支付
- R6 未付款预约在 5 分钟内付款成功 → 转为**已确认**。
- R7 重复支付成功通知**不得重复确认**（幂等）。
- R8 预约已关闭（超时取消/主动取消）后收到支付成功 → **登记支付异常记录并退还款项**，不恢复预约。
- R9 支付渠道可能失败/超时：订单状态不得错误前进。

### 4.3 取消与退款
- R10 已确认预约，**开始前 ≥ 2 小时**取消：自动受理，全额退款。
- R11 **开始前 < 2 小时**取消：须填写原因，进入**取消审核中**；审核期间：
  - 名额**保持占用**（不释放）；
  - 前台**不得核销**。
- R12 客服审核：批准 → 已取消（全额退款）；拒绝 → 回到已确认。
- R13 已取消预约的名额**仅释放一次**。
- R14 退款状态**独立可查询**；退款失败须可跟进、可重试；退款失败**不能**让已取消预约重新可用。
- R15 已核销、服务中、已完成的预约**不能**再走本题取消退款流程。

### 4.4 到店与履约
- R16 前台核销条件：本店 + 已确认 + 无待处理取消申请。三个条件缺一不可。
- R17 核销后服务人员可登记"服务开始""服务完成"。
- R18 **重复核销、重复完成不能重复记收入**（幂等）。
- R19 **核销与取消并发时必须得到唯一合法结果**：二者只能有一个成功，另一个失败并提示原因，预约与金额记录不受破坏。
- R20 非本店员工不能操作本店预约（权限校验）。

### 4.5 未到店与收店核查
- R21 时段结束后仍未到店的已确认预约，由店长标记**未到店**并写明原因。
- R22 本题约定：未到店**不自动退款**；用户可查看该结果。
- R23 店长日清查询须能分别看到：各时段有效预约、已完成、已取消、未到店、退款待处理记录。
- R24 已收款、已退款、未退款金额须能从记录核查；**不能把所有已付款都计作已完成服务**。

## 5. 预约状态机（核心）

```
待支付(PENDING_PAYMENT)
  ├─ 5分钟未付款 ──────────────→ 已取消(CANCELLED/超时)   [释放名额]
  ├─ 用户主动取消 ─────────────→ 已取消(CANCELLED/主动)   [释放名额]
  ├─ 支付成功(首次) ───────────→ 已确认(CONFIRMED)
  └─ 支付成功(重复通知) ────────→ 保持原状态(幂等)

已确认(CONFIRMED)
  ├─ ≥2小时前取消 ─────────────→ 已取消(CANCELLED/提前)   [释放名额+自动全额退款]
  ├─ <2小时申请取消 ───────────→ 取消审核中(PENDING_REVIEW) [名额保持,禁止核销]
  │     ├─ 客服批准 ──────────→ 已取消(CANCELLED/审核批准) [释放名额+全额退款]
  │     └─ 客服拒绝 ──────────→ 已确认(CONFIRMED)
  ├─ 前台核销 ─────────────────→ 已核销(CHECKED_IN) → 服务中(IN_SERVICE) → 已完成(COMPLETED)
  └─ 时段结束未到店 ───────────→ 未到店(NO_SHOW, 店长标记) [不自动退款]

已关闭状态收到支付成功 → 登记支付异常(PAYMENT_EXCEPTION) + 退款, 不改变预约状态
```

状态机不变量（测试与验收的硬性检查点）：
- I1 任何时刻，每时段有效预约数 ≤ 3（并发下同样成立）。
- I2 每只宠物每时段最多 1 个有效预约。
- I3 每笔预约最多产生一次收入确认（核销时点）；取消退款不产生收入。
- I4 取消审核中的预约不可核销、名额不释放；终态释放名额只发生一次。
- I5 核销与取消并发：恰有一个操作成功。
- I6 退款记录独立存在，失败不影响预约终态。

## 6. 必须可演示的完整工作场景（验收依据）

| # | 场景 | 覆盖规则 |
|---|---|---|
| S1 正常接待 | 店长发布时段 → 用户预约付款 → 前台核销 → 服务开始/完成 → 用户与店长查询结果 | R6, R16, R17, R23 |
| S2 名额循环 | 并发抢位 → 未付款超时或主动取消 → 名额恢复 → 新用户预约成功 | R4, R5, R13 |
| S3 取消分支 | 提前取消自动受理；临近开始客服分别批准/拒绝；退款失败重试；各用户结果不同 | R10–R14 |
| S4 门店现场冲突 | 同一预约取消与核销并发；重复核销；非本店员工操作 | R18–R20 |
| S5 收店核查 | 同日含已服务、取消退款、未到店、退款失败四种记录，店长分别核查 | R21–R24 |

## 7. 技术边界

- Go 实现核心业务；简单 HTML 页面（按角色分四组页面）；不强制微服务。
- 数据库持久化核心数据，服务重启后结果可查（选型：SQLite，嵌入式、零部署、单文件，适合单机教学场景并支持事务与并发控制）。
- 支付/退款渠道为可控 HTTP 模拟服务，可触发成功、失败、超时、重复通知。
- 教学时钟：取消政策的 2 小时与未付款 5 分钟支持可配置缩短以便演示，测试与演示使用相同规则。
- 身份预置：页面按角色登录（简单会话），不得通过修改请求中的用户编号越权。

## 8. 假设清单（题面未明确、本方案采用的处理）

| # | 假设 | 理由 |
|---|---|---|
| A1 | "有效预约"包含待支付、已确认、取消审核中、已核销、服务中 | 这些状态均占用名额或履约中 |
| A2 | 取消审核超时未处理：预约保持审核中，时段结束后随"未到店"或人工处理，不自动批准 | 题面未定义审核时限，不做猜测性行为 |
| A3 | 退款失败由客服发起重试；重试次数不设上限，失败记录保留 | 题面要求"退款失败需要跟进" |
| A4 | 支付异常退款与取消退款使用同一退款记录机制 | 统一金额核查口径 |
| A5 | 未到店由店长在时段结束后手动标记，标记后为终态不可逆 | 题面称"标记"，按终态处理 |
| A6 | 模拟支付的通知以回调接口方式到达服务端，重复通知用同一支付单号识别 | 符合常见支付渠道模型 |
| A7 | 预置账号即角色登录入口，会话内记录用户/员工身份 | 题面允许账号预置 |

## 9. 验收条件（DoD 摘要）

1. S1–S5 五个场景均可实际操作、有持久化结果，非静态页面或写死结果。
2. 状态机不变量 I1–I6 全部有对应测试通过，含并发用例（-race）。
3. 自编核心业务包单元测试语句覆盖率 ≥ 85%。
4. 店长日清页面金额可勾稽：已收款 = 已完成收入 + 已退款 + 未退款（含支付异常退款）。
5. 越权操作（改用户编号、非本店员工）被拒绝并留有记录。
